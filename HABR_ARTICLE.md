# Как я превратил загрузку Windows в Linux-терминал и 24-битный UEFI-видеоплеер на голом C (без единой библиотеки)

Когда нажимаешь кнопку питания на ПК, первые секунды обычно выглядят скучно: логотип материнской платы, чёрная пауза, крутящиеся точки Windows. Максимум кастомизации, до которого обычно доходят руки — поставить открытый **HackBGRT**, подменяющий картинку в ACPI-таблице `BGRT` на свой `splash.bmp`.

Но если задуматься: в момент старта UEFI-приложения (ещё *до* запуска `bootmgfw.efi` и ядра `ntoskrnl.exe`) в нашем полном распоряжении уже находятся 64-битный процессор в Long Mode, гигабайты оперативной памяти, прямой фреймбуфер видеокарты и сервисы прошивки `EFI_BOOT_SERVICES`. Никакого планировщика ОС, никаких антивирусов, никакого оверхеда.

Сначала захотелось просто подшутить: сделать так, чтобы при включении ПК вместо логотипа материнки на экран со скоростью пулемёта вылетал правдоподобный лог ядра Linux (`dmesg` + цветной `systemd`), а потом как ни в чём не бывало грузилась Windows. Но аппетит пришёл во время еды — и к концу ночи проект эволюционировал в полноценный **24-битный полноэкранный UEFI-видеоплеер** (`320×180` → `1920×1080` / `2560×1440` при честных `24 FPS`), который крутит 34-секундный ролик по Backrooms с межкадровым сжатием, мгновенно скипается по Пробелу, а на этапе подхвата ядра Windows ещё и передаёт эстафету оригинальному HackBGRT, чтобы вместо чёрного экрана светил кастомный `splash.bmp`.

Под катом — разбор всех реальных инженерных граблей, на которые мы наступили по дороге: от зажатой в `80×25` консоли прошивки и ошибок линковки `___chkstk_ms` до поиска пропавшего изохронного планировщика в USB-драйвере `XhciDxe`.

## Архитектура цепочки загрузки (и как не перенастраивать BIOS)

Если у вас уже стоит [HackBGRT](https://github.com/Metabolix/HackBGRT), установщик создаёт в NVRAM загрузочную запись, указывающую на `\EFI\HackBGRT\loader.efi`. В стандартной конфигурации с поддержкой Secure Boot внутри папки лежит следующая матрёшка:

1. `\EFI\HackBGRT\loader.efi` — это на самом деле подписанный сертификатом Microsoft загрузчик **Red Hat Shim** (`shimx64.efi`). Трогать его нельзя.
2. Shim проверяет MOK-базу и секцию `.sbat`, после чего жёстко ищет и запускает бинарник **`\EFI\HackBGRT\grubx64.efi`** (куда HackBGRT при установке кладёт самого себя).

Это открывает идеальную точку входа без единой правки записей BIOS/BCDEdit:
* Переименовываем оригинальный `grubx64.efi` в `grubx64.efi.bak`.
* На место `grubx64.efi` кладём наше кастомное UEFI-приложение на чистом C17 (`-ffreestanding -nostdlib`).
* Отработав лог и видеоролик, наше приложение вызывает `BS->LoadImage()` и `BS->StartImage()` для `grubx64.efi.bak` → оригинальный HackBGRT за 15 миллисекунд прописывает `splash.bmp` в таблицу `ACPI BGRT` и запускает штатный `\EFI\Microsoft\Boot\bootmgfw.efi`.

Чтобы собирать `.efi` под Windows или WSL за пару секунд без гигантского дерева EDK2 и даже без линковки `crt0-efi-x86_64.o` из `gnu-efi`, достаточно обычного `x86_64-w64-mingw32-gcc`: ведь UEFI использует родной для Windows формат **PE32+**, только с кодом подсистемы `10` (`EFI_APPLICATION`) и соглашением о вызовах Microsoft x64 ABI (`__attribute__((ms_abi))`):

```makefile
CC      := x86_64-w64-mingw32-gcc
CFLAGS  := -std=c17 -O2 -Wall -Wextra -ffreestanding -fno-stack-protector \
           -fno-stack-check -fno-builtin -fshort-wchar -mno-red-zone \
           -mno-mmx -mno-sse -mno-stack-arg-probe
LDFLAGS := -nostdlib -shared -Wl,-dll -Wl,--subsystem,10 -e efi_main
```

Казалось бы, пара флагов — но обратите внимание на два неочевидных момента:
1. **`-mno-stack-arg-probe`**: в Windows x64 ABI любая функция с локальным фреймом стека `>= 4096` байт неявно вставляет вызов `___chkstk_ms` для прощупывания сторожевых страниц. В режиме `-nostdlib` никакой `libgcc`/CRT нет, и линкер тут же падает с `undefined reference to ___chkstk_ms`. Поэтому крупные буферы в UEFI всегда выделяем в куче через `BS->AllocatePool(EfiBootServicesData, ...)`, а пробинг стека глушим флагом.
2. **Секция `.sbat`**: современные сборки Shim (15.x / 16.x) наотрез отказываются грузить PE-образ даже с добавленным в `MokManager` хешем, если внутри бинарника нет секции `.sbat` с метаданными поколения безопасности:

```c
__attribute__((used, section(".sbat")))
const char kSbatMetadata[] =
    "sbat,1,SBAT Version,sbat,1,https://uefi.org/\n"
    "linuxsim,1,Custom,LinuxBootSim,1.1,https://local.invalid/\n";
```

## Грабли №1. Фейковый Linux, засада `80×25` в `ConSplitterDxe` и потолок в 16 цветов

Первым делом мы собрали двухэтапную имитацию загрузки Linux:
* **Этап 1 (`dmesg`):** 56 плотных строк инициализации `BIOS-e820`, `ACPI RSDP/XSDT/FADT/MCFG/DMAR`, `SLUB`, `x2APIC`, шин `PCIe`, очередей `NVMe` и `USB xHCI`, вылетающих пулемётной очередью за ~1.2 секунды (`5–15 мс` на строку).
* **Этап 2 (`systemd`):** 50 строк графа служб с ярко-зелёным `[  OK  ]` (`EFI_LIGHTGREEN`), голубыми путями устройств (`EFI_LIGHTCYAN`: `/dev/nvme0n1p1`, `/boot/efi`, `enp4s0`) и неравномерным темпом — пачки сокетов пролетают рывками по `8–20 мс`, а на `udevd`, `fsck` и `networkd` происходят реалистичные «затупы» на `120–190 мс`.

Для живого разброса таймингов без единого системного генератора случайных чисел отлично подошёл аппаратный счётчик тактов процессора **`RDTSC`**, замешанный в `xorshift64*` (напрямую брать `rdtsc() % N` нельзя — на многих современных CPU младшие биты `TSC` тикают с фиксированным множителем шины):

```c
static UINT32 RdtscJitterUs(UINT32 lo_us, UINT32 hi_us) {
    static UINT64 rng = 0x6a09e667f3bcc908ULL;
    UINT32 eax = 0, edx = 0;
    __asm__ __volatile__("rdtsc" : "=a"(eax), "=d"(edx));
    rng ^= ((UINT64)edx << 32) | eax;
    rng ^= rng >> 12;
    rng ^= rng << 25;
    rng ^= rng >> 27;
    UINT64 mixed = rng * 0x2545f4914f6cdd1dULL;
    return lo_us + (UINT32)((mixed >> 16) % (hi_us - lo_us + 1U));
}
```

### Почему консоль упорно оставалась крупной (`80×25`)?
По спецификации UEFI текстовая консоль `SystemTable->ConOut` поддерживает перечисление режимов через `QueryMode(ConOut, mode, &cols, &rows)`. На мониторе `1920×1080` шрифт `8×19` даёт просторную сетку **`240×56`**. Но на реальных платах с прошивками AMI Aptio V `SystemTable->ConOut` указывает не напрямую на монитор, а на виртуальный мультиплексор **`ConSplitterDxe`**, который объединяет видеовыход (`GraphicsConsoleDxe`) и последовательный порт (`TerminalDxe` / Serial Redirection).

И вот сюрприз: `ConSplitterDxe` строит список доступных текстовых режимов как **пересечение** возможностей всех подключённых консолей! Поскольку виртуальный COM-порт умеет только `80×25` (максимум `100×31`), общий `SystemTable->ConOut` режет все высокие режимы.

**Решение:** сначала переключаем все физические видеовыходы `EFI_GRAPHICS_OUTPUT_PROTOCOL` (`GOP`) в максимальное нативное разрешение (отсекая режимы `PixelBltOnly`), а затем через `LocateHandle(ByProtocol, &SIMPLE_TEXT_OUT_PROTO_GUID, ...)` ищем тот экземпляр `SimpleTextOutput`, на дескрипторе которого **одновременно висит протокол `GOP`**. Это и есть чистый аппаратный `GraphicsConsoleDxe` нашего монитора без примеси COM-порта — и он послушно включает мелкий шрифт `240×56` (или `320×75` на 2K)!

### Тупик 16 цветов `ConOut`
Когда вслед за логом мы попробовали отрендерить в текстовой консоли ASCII-видеоклип (`140×42` символов), вскрылось второе ограничение: `ConOut->SetAttribute()` принимает всего **4 бита цвета текста** (`0x00..0x0F` — классическая 16-цветная палитра времён EGA). В ней есть ядовито-жёлтый `0x0E` и тёмно-коричневый `0x06`, но нет ни полутонов, ни плавных градиентов освещения.

Чтобы уйти от 16 цветов к миллионам оттенков 24-битного RGB, оставался один путь — рисовать напрямую через **`EFI_GRAPHICS_OUTPUT_PROTOCOL->Blt()`**.

## Грабли №2. Сжимаем 34 секунды `320×180` 24-bit видео в один `.efi` и держим железные 24 FPS

Считаем арифметику «в лоб»:
* Разрешение сетки: **`320×180`** (`57 600` тайлов на кадр). Почему именно `320×180`? Потому что оно нацело, без единого пикселя чёрных рамок, масштабируется на все популярные `16:9` мониторы:
  * `×6` → ровно **`1920×1080`** (Full HD);
  * `×8` → ровно **`2560×1440`** (2K QHD);
  * `×12` → ровно **`3840×2160`** (4K UHD).
* Длительность ролика: `34 секунды` при `24 FPS` = **`816 кадров`** (`47 001 600` пикселей суммарно).
* В сыром 32-битном `BGR0` это весило бы **~180 МБ** — раздел FAT32 ESP (который Windows по умолчанию размечает всего на `100 МБ`!) просто лопнет. Нам нужно было уложиться в **8–13 МБ** без тяжёлых декодеров вроде H.264/MPEG, которые пришлось бы тащить в bare-metal C.

### Конвейер сжатия в Python (`tools/video_to_color_ascii.py`)
1. **Резкость без усиления шума:** при даунскейле кадра до `320×180` (`cv2.INTER_AREA`) мы поднимаем контраст (`×1.09`) и накладываем **пороговый `unsharp mask`** (`sigma = 0.85`, усиление только там, где `|detail| >= 3.5`). Глаза персонажей, контуры и мелкие субтитры становятся бритвенно резкими, а плоские стены с артефактами YouTube-сжатия остаются гладкими и отлично сжимаются.
2. **Адаптивная 255-цветная 24-битная палитра:** по выборке из 80 кадров со всего клипа строится оптимальная палитра (`MedianCut + K-Means`) на `255` цветов (`0..254`), сразу упакованная в `UINT32` (`0x00RRGGBB` — побайтово совпадает со структурой `EFI_GRAPHICS_OUTPUT_BLT_PIXEL { Blue, Green, Red, Reserved }`).
3. **Temporal-Delta RLE в `UINT16`:** индекс **`255`** зарезервирован под команду *«оставить следующие `N` тайлов такими же, какие уже лежат в буфере экрана с прошлого кадра»*. Если RGB пикселя изменился слабее порога `diff_tol`, мы вообще его не перерисовываем! Каждая пара `(color_idx, run_length)` пакуется в одно 16-битное число `UINT16`:
   * Во-первых, весь 34-секундный HD-поток ужимается до **~8–12.7 МБ** секции `.rdata`.
   * Во-вторых, массив скаляров `0xRRCCU` компилируется в `gcc` за 5 секунд, тогда как миллионы вложенных структур `{{c, len}, ...}` заставляют парсер C строить гигантское AST-дерево на гигабайты памяти.

### 64-битный рендер, грязные полосы и калибровка `RDTSC`
Чтобы на `2560×1440` (`14.7 МБ` на кадр!) гарантированно не проседать ниже `24 FPS`:
* Вместо побайтового заполнения структуры `EFI_GRAPHICS_OUTPUT_BLT_PIXEL` функция `FillPixels32()` склеивает два 32-битных пикселя в один `UINT64` и заливает горизонтальные прогоны в RAM развёрнутым циклом по **8 пикселей (32 байта) за итерацию**, а нижнюю линию каждого тайла красит из предрассчитанной притемнённой палитры (`7/8` яркости), сохраняя приятную текстуру терминальной решётки:

```c
static inline void FillPixels32(UINT32 *dst, UINTN count, UINT32 color32) {
    UINT64 pair = ((UINT64)color32 << 32) | (UINT64)color32;
    UINT64 *dst64 = (UINT64 *)dst;
    UINTN pairs = count >> 1;
    while (pairs >= 4U) {
        dst64[0] = pair; dst64[1] = pair;
        dst64[2] = pair; dst64[3] = pair;
        dst64 += 4;
        pairs -= 4U;
    }
    while (pairs--) *dst64++ = pair;
    if (count & 1U) *(UINT32 *)dst64 = color32;
}
```

* За кадр отслеживаются `dirty_y_min` и `dirty_y_max` — в видеопамять по шине PCIe через **единственный вызов `gGop->Blt(..., EfiBltBufferToVideo, ...)`** копируется только реально изменившаяся полоса строк без тиринга и мерцания.
* **Точный тайминг кадра:** если после отрисовки кадра тупо вызывать `gBoot->Stall(41667)` (для `24 FPS`), а сам рендер + `Blt` заняли, скажем, `8 мс`, то 34-секундное видео растянется на 41 секунду. Поэтому перед стартом цикла мы за `20 мс` калибруем частоту `RDTSC` (`tsc_per_us`), замеряем точное время рендера каждого кадра и спим ровно `41667 - elapsed_us` микросекунд!
* А чтобы не перезагружать компьютер после каждой правки шейдера резкости, мы написали скрипт живого превью `tools/preview_terminal.py`, который крутит ролик прямо в окне Windows Terminal на реальных `24 FPS` через 24-битные ANSI-коды и полублоки `▀` (два вертикальных пикселя в одном знакоместе).

## Бонус: «А как прикрутить звук в UEFI?!» — история одной заглушки в `XhciDxe`

Логичный следующий вопрос: видео идёт в Full HD на 24 FPS, а реально ли пустить параллельно музыку до старта Windows? Спойлер: **зависит от того, куда воткнуты ваши наушники**.

В самом стандарте UEFI «из коробки» звукового протокола в `SystemTable` нет вообще. На типичном игровом ПК есть три физических маршрута вывода звука:
1. **Встроенный кодек материнки (например, Realtek `ALC897` на шине Intel/AMD HDA)** — обычные 3.5 мм джеки.
2. **HDMI / DisplayPort аудио на видеокарте** — тоже контроллер HDA, если в мониторе есть динамики.
3. **USB-гарнитура или беспроводной USB-донгл (например, Logitech)** — стандарт USB Audio Class поверх `xHCI`.

Для **3.5 мм и HDMI (HDA)** задача решается на удивление красиво! В экосистеме загрузчика OpenCore (Acidanthera) есть готовый открытый драйвер **`AudioDxe.efi`** (сделанный для воспроизведения фирменного *boot chime* при включении Mac). Достаточно подгрузить `AudioDxe.efi` через `LoadImage` + `StartImage`, и в системе появляется протокол `EFI_AUDIO_IO_PROTOCOL` с асинхронным методом **`StartPlaybackAsync()`**. Вся прелесть HDA в том, что звук качается через **аппаратный кольцевой DMA-буфер (`BDL — Buffer Descriptor List`)**: звуковая карта сама читает PCM-семплы из оперативки в фоне, вообще не нагружая CPU, пока наш цикл спокойно рисует видео.

А вот если ваш единственный звук на ПК — это **USB-донгл гарнитуры**, в UEFI ждёт холодный душ. Потоковое аудио в USB Audio Class передаётся не обычными `Bulk`-пакетами (как данные с флешки), а **изохронными передачами (`Isochronous Transfers`)** по жёсткому расписанию микрокадров. Казалось бы, в протоколе `EFI_USB2_HC_PROTOCOL` даже описан метод `IsochronousTransfer`! Открываем исходный код референсного драйвера `MdeModulePkg/Bus/Pci/XhciDxe` в EDK2 (на базе которого собраны прошивки 99% материнских плат) и видим шедевр лаконичности:

```c
EFI_STATUS EFIAPI XhcIsochronousTransfer(...) {
    return EFI_UNSUPPORTED;
}
```

Разработчики BIOS просто не включают изохронный планировщик TRB-колец в прошивку, потому что ни клавиатуре, ни флешке он не нужен. А попытка отобрать контроллер `xHCI` у BIOS через `DisconnectController`, чтобы рулить его MMIO-регистрами самостоятельно, тут же отрубает штатный опрос USB-клавиатуры (`ReadKeyStroke` перестанет ловить клавишу пропуска!), пока вы рядом с драйвером USB-звука не напишете ещё и собственный стек USB HID с аккуратным возвратом контроллера перед стартом `bootmgfw.efi`. Поэтому для чистого и надёжного UEFI-бута без риска повесить USB мы оставили молниеносный беззвучный видеоплеер.

## Безопасность, защита от бутлупа и быстрый откат

Эксперименты с разделом `EFI System Partition` требуют аккуратности, поэтому в код сразу заложены предохранители:

1. **Никогда не трогаем `\EFI\Microsoft\Boot\bootmgfw.efi`:** вся работа идёт в изолированной папке `\EFI\HackBGRT\`. Штатная запись `Windows Boot Manager` всегда остаётся нетронутой в загрузочном меню материнки (`F8` / `F11` / `F12` при включении).
2. **Защита от бесконечной рекурсии (`IsValidBackupEfi`):** что будет, если при обновлении случайно скопировать наш кастомный `grubx64.efi` поверх бэкапа `grubx64.efi.bak`? Обычный чейнлоадер ушёл бы в вечный цикл, крутя ролик по кругу до бесконечности. Наш загрузчик перед вызовом `LoadImage` сканирует `.bak`-файл в памяти и проверяет, что в нём нет ни нашей сигнатуры `LinuxBootSim`, ни строки `UEFI shim`. Если бэкап испорчен — он мгновенно пропускается, и управление уходит напрямую в `\EFI\Microsoft\Boot\bootmgfw.efi`.
3. **Мгновенный пропуск:** опрос `ConIn->ReadKeyStroke` выполняется дважды за каждый кадр — нажатие любой клавиши (`Пробел`, `Enter`, `Esc`) в ту же миллисекунду освобождает буфер через `FreePool` и передаёт управление Windows.
4. **План «Б» (откат за 30 секунд):** если что-то пошло не так (например, забыли зарегистрировать новый хеш `grubx64.efi` в `MokManager` при включённом Secure Boot), достаточно при включении ПК нажать `F11`/`F12`, выбрать в меню BIOS штатный **Windows Boot Manager**, загрузиться в систему и вернуть исходный файл двумя командами в PowerShell от администратора:
   ```powershell
   mountvol S: /S
   Copy-Item "S:\EFI\HackBGRT\grubx64.efi.bak" "S:\EFI\HackBGRT\grubx64.efi" -Force
   mountvol S: /D
   ```
